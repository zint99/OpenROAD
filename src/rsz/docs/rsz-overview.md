# RSZ 模块总览：通过调整电路修复电气和时序问题

`rsz`（Resizer）根据单元库、时序分析和连线估计，调整单元型号、插入或删除缓冲器，并采用其他保持逻辑功能的变换，改善电气约束、时序、面积或功耗。虽然名字强调“调整尺寸”，它实际处理的范围比换大、换小单元更广。

本文依据 OpenROAD 提交 `a5a08e8356` 的文档与源码编写。配置详见 [RSZ README](../README.md)。

## 1. 为什么综合后的电路还需要修复？

逻辑综合已经选择了一组单元来实现功能，但物理设计进一步确定了真实距离和负载。一个在综合阶段足够强的驱动单元，到了版图上可能需要带动很长的导线，信号变慢，甚至无法在时钟要求的时间内到达。

CTS 又会改变路径两端的时钟到达时间，布线绕行会增加导线负载。这些变化使优化必须贯穿布局、时钟树和布线等阶段。

RSZ 需要分清三类问题：

| 问题 | 通俗含义 | 常见修复方向 |
| --- | --- | --- |
| 电气限制违例 | 驱动的负载过大、连接的接收端过多，或信号边沿过慢 | 分担负载、插入缓冲器、调整驱动能力。 |
| Setup：建立时间违例 | 数据到达得太晚，赶不上接收寄存器的采样要求 | 缩短数据传播时间。 |
| Hold：保持时间违例 | 新数据到达得太早，破坏接收寄存器需要保持旧数据的时间 | 有选择地增加最短数据路径的延迟。 |

Setup 和 hold 的方向不同，修复其中一个可能恶化另一个，因此需要共同检查。

## 2. 输入和输出

| 输入 | 用途 |
| --- | --- |
| 当前网表和物理位置 | 确认可修改单元、连接关系和连线几何。 |
| Liberty 库及物理单元模板 | 提供逻辑等价候选、驱动能力、时序、面积与功耗特性。 |
| SDC、时钟状态与分析角 | 确定目标时序，以及在什么条件下判断违例。 |
| 当前阶段的寄生参数 | 用布局或全局路径估计，或使用提取结果，评估导线电阻、电容。 |
| 可用单元、禁止修改对象与面积预算 | 限制优化允许采用哪些变换。 |

主要输出是**修改后的网表、单元型号、缓冲器及相应位置等数据库状态**，加上违例和质量变化报告。优化结束后，仍要确认新增或变大的单元是否合法落位，受影响的连线和寄生模型是否已更新。

`dont_use` 主要限制某类库单元参与选择，`dont_touch` 主要保护设计对象不被修改；理解二者的用途，比记住全部命令选项更重要。

## 3. 核心方法：提出修改，用时序验证收益

```mermaid
flowchart LR
    A[当前时序与电气违例] --> B[选择目标路径或负载]
    B --> C[尝试单元替换、缓冲等变换]
    C --> D[更新相关分析]
    D --> E[评估收益和约束]
    E --> F[保留或撤销修改]
    F --> A
```

**修复电气问题。** 对负载过大的驱动端，可以将一批接收端分组，交给缓冲器驱动；对较长导线，可以沿途增加缓冲；对边沿过慢的情况，可以选择更合适的单元型号。

**修复建立时间。** 可用变换包括增强驱动能力、缓冲、调整等价输入引脚、复制驱动单元以分担负载，以及库允许时的阈值电压型号替换等。阈值电压影响速度和漏电功耗；可选变换取决于库、流程设置和当前优化策略。

**修复保持时间。** 常通过在过快的数据支路上插入延迟来改善。位置必须谨慎选择，避免使共享路径上的其他端点发生 setup 违例。通常在时钟树建立、时钟传播得到适当建模后，保持时间修复才有可靠依据。

**在满足约束后回收资源。** 对有较多时序余量的区域，可以在适用设置下尝试减小单元或降低功耗。但任何节省都需要重新验证，不能只看单元面积表。

当前实现将 setup 优化组织为顶层优化器和可选策略、变换执行等部分；理解“目标选择—尝试修改—更新分析—接受或回退”这条主线，比先记住全部策略名称更有帮助。

## 4. 典型场景：为什么换大单元不一定更快？

假设 A 驱动 B，B 再驱动一条长线。把 B 换成更强的单元，可能使 B 的输出更快，但更大的 B 通常也给 A 带来更大输入负载。A 变慢后，整条路径的净收益未必为正；更大的单元还可能挤占邻居位置，使合法化后线长增加。

这说明优化应看路径和共享网络，不能只比较单个单元的延迟。

常见使用时机包括布局后修复长线和负载问题、CTS 后修复 setup/hold，以及全局布线和寄生估计更新后的再次优化。不同阶段依赖不同精度的物理信息，早期修复不是最终保证。

## 5. 怎样判断结果及模块协作？

| 指标 | 含义 |
| --- | --- |
| WNS | 最差负裕量，反映最严重的时序违例。 |
| TNS | 各违例端点负裕量的汇总指标，反映违例的整体程度。 |
| 电气违例数 | 检查 slew、负载电容等限制的修复情况。 |
| 单元面积、缓冲器数和功耗 | 衡量为修复付出的资源代价。 |
| 合法性、拥塞及布线后时序 | 确认局部优化在后续实现中仍然有效。 |

比较时应保持分析角、时钟模型和寄生来源一致。只改善 WNS，可能遗漏大量其他违例；只减少违例，也可能耗尽可放置空间。

`sta` 负责计算，`dbSta` 负责数据库集成，寄生估计组件提供导线模型，`dpl` 负责合法落位，`grt` / `drt` 处理路由。RSZ 改变电路后，这些环节需要按流程协同更新。

## 6. 三类角色的后续学习路径

- **OpenROAD 工具使用者：** 先读懂一条 setup 和一条 hold 报告，再结合 [README](../README.md) 和 [测试目录](../test) 比较修复前后的路径、单元数和面积。每次记录使用的寄生来源与时钟状态，避免把模型变化误当成优化收益。
- **OpenROAD 其他模块开发者：** 从 [Resizer.hh](../include/rsz/Resizer.hh)、[Resizer.cc](../src/Resizer.cc) 和 [OdbCallBack.cc](../src/OdbCallBack.cc) 理解调用及数据生命周期。重点确认自己的变更是否更新了网表、时序和寄生状态，以及何时触发合法化。
- **RSZ 模块开发者：** 按 [RepairDesign.cc](../src/RepairDesign.cc) → [Optimizer.cc](../src/Optimizer.cc) / [policy 目录](../src/policy) → [MoveCommitter.cc](../src/MoveCommitter.cc) → [RepairHold.cc](../src/RepairHold.cc) 阅读。用共享扇出、紧张 setup/hold 和面积受限场景检验收益评估与回退，再追踪完整流程质量。
