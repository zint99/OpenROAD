# CTS 模块总览：把时钟可靠地送到每个接收端

`cts`（Clock Tree Synthesis，时钟树综合）为时钟信号构建分级分叉的缓冲网络，使分布在芯片各处的寄存器能够获得质量合适、到达时间受控的时钟。它会新增单元、拆分网络并安排缓冲器位置，是一次实际的电路结构修改。

本文依据 OpenROAD 提交 `a5a08e8356` 的文档与源码编写，面向初次接触物理设计的读者。参数用法见 [CTS README](../README.md)。

## 1. 为什么需要时钟树？

寄存器可以理解为在时钟“打拍子”时保存数据的电路。一个时钟源可能要驱动成千上万个寄存器；接收端越多、距离越远，直接连接的电气负担就越大。实际导线有电阻、电容，信号传播需要时间，边沿也会变缓。

CTS 在时钟源和接收端之间插入多级缓冲器。缓冲器相当于沿途的接力站：前一级带动少量后一级，末级再驱动附近的寄存器。这样既能控制每段负载，也能协调各分支的传播时间。

必须区分三个量：

| 概念 | 含义 | 为什么重要 |
| --- | --- | --- |
| 时钟延迟（latency） | 时钟从参考点传播到接收端所需的时间；比较时要使用相同参考点 | 影响时钟到达时间和接口时序。 |
| 时钟偏斜（skew） | 两个接收端的时钟到达时间之差 | 同一条数据路径两端的时钟差会改变建立、保持时间裕量。 |
| 转换时间（slew） | 信号从低电平变到高电平或反向变化的快慢 | 边沿过慢会影响单元延迟，甚至违反库规定的限制。 |

延迟短不代表偏斜小，偏斜小也不代表所有数据路径都满足时序。时钟树还需要平衡缓冲器面积、功耗和布线资源。

## 2. 输入和输出

CTS 直接使用 OpenDB 中的设计。OpenDB 是各物理设计模块共享的数据库；文件通常先被读入，再由 CTS 使用其中的信息。

| 输入 | 作用 |
| --- | --- |
| 网表与已布局的寄存器、宏块 | 网表说明连接关系，位置说明各接收端在哪里。宏块是存储器等较大的预设计电路块。 |
| 时钟定义和时序环境 | 识别时钟根、接收端，以及门控时钟等分支关系。 |
| Liberty 单元库、可用时钟缓冲器 | 提供缓冲器延迟、负载能力和引脚电容等电气信息。 |
| 导线 RC 模型 | RC 指电阻、电容，用于估计尚未详细布线的时钟连线延迟。 |
| 物理约束及构树配置 | 限制缓冲器可放位置，控制聚类、树结构和负载平衡。 |

主要输出是**插入缓冲器后的时钟网表及其物理位置**，还包括时钟子网、相关布线规则和树规模统计。某些配置会插入延迟缓冲器或用于平衡负载的单元。

CTS 之后仍需详细布局、布线和时序分析。构树使用的线长与 RC 是估计值，实际绕行、过孔和合法化位移都可能改变时钟到达时间。

## 3. 核心工作：从散布的接收端到一棵树

```mermaid
flowchart LR
    A[时钟根与接收端位置] --> B[接收端聚类]
    B --> C[建立树的分支]
    C --> D[选择并插入缓冲器]
    D --> E[平衡负载与延迟]
    E --> F[写回数据库]
    F --> G[合法化、布线、时序复查]
```

**先掌握缓冲器和导线的传播特性。** 当前实现基于 TritonCTS 2.0，通过运行时表征评估不同缓冲器、线段和负载组合的表现，为后续选择提供依据。它需要与当前库和 RC 设置匹配。

**再把附近的接收端组织起来。** 接收端称为 sink，时钟源称为 root。聚类把邻近、负载适合的 sinks 交给局部缓冲器，减少上层构树的复杂度。聚类不能只追求数量均匀：距离、引脚电容以及宏块和寄存器的差别都会影响结果。

**建立分支并安排接力站。** 树构建器采用 H-tree 风格的递归分割组织连接，结合几何位置和电气模型安排缓冲器。真实设计包含障碍和不均匀负载，最终结果不一定是一幅对称的“H”形图。

**调整不同分支的负载和延迟。** 门控单元、宏块时钟引脚、不同层级的树都可能引入差异。平衡过程中有时需要给过快分支增加延迟，或者调整末端负载。这样做的收益必须通过完整时序检查判断。

## 4. 典型场景与结果判断

最常见的场景是：标准单元已完成一版布局，时钟还主要以理想模型参与分析，此时运行 CTS，随后进入真实时钟传播条件下的优化。理想时钟是一种分析假设，并不意味着芯片上已有零延迟的导线。

例如，左侧有一组寄存器，右侧有一个大宏块。只按平面距离平衡两条分支，可能忽略宏块内部时钟路径带来的差异。需要结合宏块模型、接收端负载和构树设置，再观察两侧数据路径的建立、保持时序。

评估时至少同时看缓冲器数量、时钟延迟、偏斜、slew/电容违例，以及 CTS 后的数据路径时序。`report_cts` 的规模统计适合确认“生成了什么”；详细时序结果需要借助 STA。树规模正常不能单独证明时钟质量合格。

## 5. 与其他模块如何协作？

| 模块 | 与 CTS 的关系 |
| --- | --- |
| `gpl` / `dpl` | 提供接收端位置；DPL 还负责将新增缓冲器合法落位。 |
| `sta` / `dbSta` | 提供库和时钟语义、时序计算，并维护数据库与时序视图的关联。 |
| `rsz` | 在相应流程阶段修复电气和数据路径时序问题，配合处理 CTS 后出现的违例。 |
| `grt` / `drt` | 把时钟网络转化为全局路径及实际金属连接，结果供更准确的分析使用。 |

## 6. 三类角色的后续学习路径

- **OpenROAD 工具使用者：** 从 [simple_test.tcl](../test/simple_test.tcl) 认识库、时钟和 RC 的准备顺序，再看 [post_cts_opt.tcl](../test/post_cts_opt.tcl)。练习比较 CTS 前后的树规模、时钟传播模型和 setup/hold 报告，能够解释“为什么插树后保持时间变差”。
- **OpenROAD 其他模块开发者：** 先读 [TritonCTS.cpp](../src/TritonCTS.cpp)，确认时钟网络发现、数据库修改和后处理的边界。重点理解新增实例、子网和放置状态怎样影响自己的模块，以及何时需要重建寄生参数。
- **CTS 模块开发者：** 按 [TechChar.cpp](../src/TechChar.cpp) → [SinkClustering.cpp](../src/SinkClustering.cpp) → [HTreeBuilder.cpp](../src/HTreeBuilder.cpp) → [LatencyBalancer.cpp](../src/LatencyBalancer.cpp) 阅读。用 [测试目录](../test) 中的聚类、门控时钟和障碍场景比较修改前后的偏斜、功耗代理指标、面积与运行时间。
