# DPL 模块总览：让单元在合法位置上落位

`dpl`（Detailed Placement，详细布局）把标准单元安排到允许的放置行和站点上，消除重叠并满足放置约束，同时尽量少偏离已有布局。它既承接全局布局，也用于缓冲器插入、单元尺寸调整等操作后的再次合法化。

本文依据 OpenROAD 提交 `a5a08e8356` 的文档与源码编写。命令和配置详见 [DPL README](../README.md)。

## 1. 为什么还需要“详细”布局？

全局布局关心成千上万个单元的整体分布，优化时通常允许位置连续变化，阶段性存在重叠。制造所需的布局却有离散约束：单元必须对齐放置站点，位于允许的行内，还要避开已固定的宏块和禁止放置的区域。

可以把全局布局看作给座位安排大致分区，DPL 则负责把每个人安排到真实、可用、互不冲突的座位上。难点在于不能随意挪动：距离变化会影响导线长度和时序，也可能把拥挤问题推给邻居。

| 概念 | 含义 |
| --- | --- |
| 标准单元 | 具有规定高度、可沿放置行排列的小型逻辑单元。 |
| Row / site | Row 是放置行，site 是行内的基本离散位置或宽度单位。 |
| 合法化（legalization） | 把已有位置修正为满足放置约束的位置。 |
| 位移（displacement） | 修正前后的位置变化；过大可能破坏原有布局质量。 |
| Fence region | 限定某组实例必须放在其中的区域。 |

## 2. 输入和输出

| 输入 | 用途 |
| --- | --- |
| OpenDB 中的实例及当前位置 | 提供需要合法化的对象和希望保留的布局意图。 |
| 放置行、site 与单元物理模板 | 判断单元大小、行兼容性和可用落点。 |
| 固定实例、宏块与放置障碍 | 划分不能占用的空间，可能将一行切成多个片段。 |
| 区域、方向、间距及 padding 等约束 | 决定每个单元能放在哪里以及需要留多少空间。 |

主要输出是**合法化后的实例坐标、方向和放置状态**，以及位移与合法性检查结果。常规合法化以移动单元为主；选择 filler、decap 等相关功能时，还会新增相应物理单元。

已有合法位置仍可能因后续单元变大或新缓冲器插入而失效。因此 DPL 通常在流程中多次出现，不能只在全局布局之后运行一次就永久完成任务。

## 3. 核心工作：在有限空间内解决冲突

```mermaid
flowchart LR
    A[全局布局或优化后的单元] --> B[建立行与可用位置模型]
    B --> C[搜索候选落点]
    C --> D[协调重叠与放置规则冲突]
    D --> E[写回位置并检查]
    E --> F[后续时序分析与布线]
```

**先把版图空间转成可用位置。** 宏块、障碍和区域限制会使可用行不连续。单元高度也未必相同，多高度单元要同时满足跨行占用和相应兼容条件。

**在邻近范围内寻找候选落点。** 就近放置有助于保留全局布局成果，但最近的空隙可能太窄，或不属于该单元允许的区域。Padding 则为单元额外保留左右空间，常用于缓解引脚接入和布线压力；它也会减少可用容量。

**通过迭代协调冲突。** 当前版本默认使用 `NegotiationLegalizer`，即协商式合法化器。它结合位移和冲突代价反复调整位置，逐步消除争用。仓库还保留旧的 diamond search 引擎，可按配置选择。理解模块职责时，应以“受约束的合法落位”为主，不必先记住每项搜索参数。

**完成后再检查。** `check_placement` 用于检查实现所覆盖的放置合法性。详细布局模块还提供镜像优化、filler 插入等功能：镜像可能缩短信号引脚间距离；filler 是填充空隙、延续行内电源地轨等物理结构的单元。

## 4. 典型场景与结果判断

**全局布局后的首次合法化。** 单元大体分布合理，但局部重叠或未对齐站点。需要同时观察是否消除违例，以及平均、最大位移是否过大。

**时序优化后的再次合法化。** 一个小单元被换成更宽的强驱动单元后，会与邻居争抢位置。即使只修改一个实例，也可能引起周围一串单元移动，进而改变附近网络的长度。

**宏块周围的狭窄区域。** 总面积有空余，并不意味着每个局部区域都有可行解。某个区域可能剩下许多小空隙，却没有一个能容纳目标单元；过严的位移限制或过大的 padding 也可能导致放置失败。

遇到失败，先查区域容量、单元与行是否兼容、障碍和位移约束，而不是只增加迭代次数。成功后则重新观察时序、线长和拥塞。**放置合法只说明满足相应放置检查，详细布线仍可能遇到困难。**

## 5. 与其他模块如何协作？

| 模块 | 与 DPL 的关系 |
| --- | --- |
| `ifp` | 准备基本放置行与场地信息。 |
| `gpl` | 给出整体分布，DPL 尽量保留其位置意图。 |
| `cts` / `rsz` | 新增或调整单元后，需要配合合法化。 |
| `upf` | 电源域实现可能产生区域分组与跨域接口单元，影响放置约束。 |
| `grt` / `drt` | 使用最终引脚位置布线；DPL 的空间安排会影响引脚可达性。 |

## 6. 三类角色的后续学习路径

- **OpenROAD 工具使用者：** 从 [README](../README.md) 和 [测试目录](../test) 中选择小设计，依次观察全局布局、合法化、合法性检查。改变一次 padding 或位移限制，比较成功率、位移和布线拥塞，理解空间预算。
- **OpenROAD 其他模块开发者：** 阅读 [Opendp.cpp](../src/Opendp.cpp) 与 [dbToOpendp.cpp](../src/dbToOpendp.cpp)，理解固定状态、坐标、区域及行信息如何传递。自己的模块插入或扩宽单元后，应明确何时重新合法化和更新寄生估计。
- **DPL 模块开发者：** 按 [NegotiationLegalizer.cpp](../src/NegotiationLegalizer.cpp) → [NegotiationLegalizerPass.cpp](../src/NegotiationLegalizerPass.cpp) → [PlacementDRC.cpp](../src/PlacementDRC.cpp) → [CheckPlacement.cpp](../src/CheckPlacement.cpp) 阅读。用混合高度、碎片行、fence 和密集区域场景评估合法性、位移、运行时间及后续布线质量。
